# Projects 项目栏目设计规格

版本 1.0 · 2026 年 10 月 3 日 · 待审阅

这份规格把已经确认的方向整理为可审阅的页面设计：工作项目和个人项目放在同一个栏目，先让访客理解包子做了什么，再用图片帮助说明。范围包括项目列表、详情页，以及人物与嘉乐在该栏目中的呈现。

概念方向已经确认；以下布局细节、内容结构和验收要求是本次提案。本文尚未获书面规格批准，也不代表已经实现。审阅通过后再写实施计划；所有栏目完成设计后统一安排内容迁移，不单独发布 Projects。

## 一 已确认的方向与当前基础

### 已确认

- 列表以项目名称、一句话简介和个人角色为主，图片为辅；工作与个人项目都可以收录。
- 详情说明问题、个人贡献、过程和结果，按实际材料取舍。
- 人物像在安静地介绍项目，嘉乐在旁边；不增加抢眼的新交互。
- 沿用暖白内容纸、炭黑文字、低对比点阵环境、左侧导航与角色。手机仍是文章、照片、简历、项目四项单行导航。
- 文案少而准确。不添加“挑一个项目看看”等教访客操作的标题，也不把栏目做成大图作品墙。
- 内容、角色素材与发布分别审批。设计通过不等于项目事实、截图或新角色姿态获得公开许可。

### 当前源码已核实

本次只读核对源码归档 v10 与实施报告 v12。现有站点使用 Astro 静态构建与 Markdown Content Collections；已有 `/projects` 和 `/projects/<slug>`，共享 ShellLayout、Editorial 排版和页面切换。

Projects 当前只有三个草稿，均不满足公开门禁。现有列表是日期、标题、简介与详情链接；详情渲染标题、日期、简介、正文和可选外链。当前 schema 尚无角色、工作／个人类型和项目状态字段，下文相关能力均为新增设计，不能视为现有功能。

当前全站设计规范 v2.8、D-127 内容门禁及 D-148 至 D-155 的有效规则优先。旧五入口、手写手账字体、首页左文右人物、强制首推进行中项目等历史写法，不作为本次排版依据。已有文章、相册和开场保持各自已确认规则。

## 二 项目列表

### 信息顺序

页面标题只保留“项目”。标题下面直接进入列表，不重复写栏目说明和引导语。每个条目按以下顺序呈现：

1. 项目名称，作为主要详情链接。
2. 一句话说明项目解决什么问题或做了什么。
3. “我负责……”的具体角色范围，尽量一行，必要时自然换行。
4. 较轻的“工作”或“个人”标签，以及有事实依据时才出现的年份或项目状态。

名称与个人贡献在桌面、手机、键盘操作和无 JavaScript 时都直接可读。不能把“我做了什么”藏在悬停态、图片说明或点击后的第二层。

条目使用纵向编辑列表，以留白和细分隔线区分。不套厚边框、阴影卡片，不增加每条重复的“查看项目”按钮。标题链接有足够点击区域，悬停和键盘聚焦都有清楚反馈；非链接文字不伪装成可点击控件。

### 图片与排序

有合适且已批准的图片时，桌面可在条目文字右侧放一张小图，宽度不超过条目可用宽度的三分之一。不为图片设置大幅统一图槽，也不让它比标题和个人贡献更抢眼。界面截图优先完整呈现，避免把关键文字裁掉；摄影或概念图的裁切须单独确认。

手机改为单列，文字在前，辅助图随后。没有图片的项目正常成立，不补灰框、假封面或装饰图。图片若提供必要信息，应在正文中有对应解释；不采用只有 hover 才能看见的项目预览。

本版沿用真实记录日期倒序，不自动把“进行中”当作精选，也不新设人工置顶机制。日期只表达已确认的时间含义，不把记录日期暗示为任职或交付周期。工作与个人混排，通过轻标签区分。本版不做筛选、搜索或分页；条目增多后再按真实浏览需求决定，不先摆空筛选器。

## 三 项目详情

### 首屏先说清个人责任

详情顶部提供“返回项目”，然后依次呈现名称、一句话简介、个人角色，以及可选的项目类型、时间范围与状态。首屏不强制放大封面；首张图只有在能帮助理解项目时才使用。

“我负责……”说明本人承担的范围，不把团队或公司的全部成果归为个人完成。参与、独立完成、主导等表述必须能由真实材料支持。必要时简短说明团队分工，但不推断同事姓名、客户身份或内部职责。

### 正文结构

采用以下阅读顺序，章节标题可按真实内容写得更具体：

- **问题**：当时需要解决什么，面向谁，有哪些关键约束。
- **我的贡献**：我具体负责、决定和交付了什么。不能只列工具或技术栈。
- **过程**：保留能解释判断的少数关键步骤，包括取舍、迭代或失败后的修正。图片跟随对应段落，不堆在页首。
- **结果**：实际交付与观察到的变化。没有结果数据就不写百分比、增长量或影响人数；进行中项目可写目前完成的部分。
- **反思**：有真实结论才出现，不强制凑齐章节。

问题与个人贡献是公开案例的最低解释要求，其余章节按材料出现。无结果、无图、无外链都不生成空标题或占位模块。没有可公开的证据时，明确可描述的范围；不足以说明个人工作时继续保留草稿。

结果中的数字需有来源、统计范围和时间口径，并经过用户确认；团队结果须注明归属。工作项目先检查保密约定、客户资料、内部界面、账号信息与同事个人信息，未经确认不把这些材料移入公开资源。必要时使用经批准的脱敏图或纯文字案例；脱敏不自动等于可公开。

### 阅读与离开

正文复用现有文章字体、行距、图注和约 720px 的舒适阅读宽度，不重新建立一套长文样式。Projects 默认不启用文章的嘉乐追球、百分比进度或章节短线；若未来真实案例足够长，再单独评估目录是否有用，手机继续不增加文章阅读辅助。

项目外链按实际目标标为“访问项目”或“查看代码”等，不显示无效或未批准链接。页尾只保留必要外链和“返回项目”，不添加推荐墙、打分、点赞或完成庆祝。

## 四 人物 嘉乐与响应式

人物继续位于共享左侧环境区，面向内容，保持安静介绍的感觉。嘉乐在旁边停留，不跟随鼠标、追逐卡片、触发气泡或代替导航。两者都是装饰，无键盘焦点，不遮挡链接、正文和焦点轮廓。

“介绍项目”的新姿态只是视觉意图，不表示素材已经完成或批准。若需派生姿态，应单独出图、独立保存并由用户看图确认；不得覆盖现有角色、Manifest 或把相册未批准候选挪来使用。素材未通过时复用适合的现有已批准静态角色；没有合适资产则暂不显示对应装饰，不用生成占位角色填满空间。

桌面沿用全站左栏：大于 1050px 为 300px，768–1050px 为 242px。Projects 在内容纸内调整文字与小图，不挤占左侧导航。小于等于 767px 时采用单列列表和正文，角色区域缩减，保留四项导航一行及每项可操作面积，不为角色推迟正文出现。

项目名、角色说明和标签都允许自然换行，不以省略号隐藏核心信息。窄屏与 200% 浏览器缩放下不得产生整页横向滚动；表格或代码如确有必要，只在自身容器内滚动。

## 五 内容与实现边界

### 拟议内容字段

保留现有 title、intro、date、link、draft、approved、updated 与封面相关字段。拟新增 role 和 kind：role 是可公开的个人角色描述，kind 仅区分工作与个人。公开项目必须具备两者；旧草稿可暂缺，不能为了通过校验自动补出事实。

另可选项目时间范围与 status。时间范围必须来自确认材料；status 只在“进行中”或“已完成”能准确表达情况时使用，也可以不显示。结束参与不自动等于项目已完成。具体字段名、校验形式和模板同步留给实施计划，但不能把状态与内容批准混为一谈。

正文仍由 Markdown 维护，不新增 CMS、运行时数据库或上传后台。只有 draft 为 false 且 approved 为 true 的内容进入列表、详情、首页引用及分享元数据；schema、模板和全部消费端必须一致。新增展示字段不能放宽既有门禁。

### 架构职责

沿用现有静态数据链路：内容集合在构建期通过共享门禁，列表读取摘要字段，详情渲染同一条记录正文，页面继续使用共享 ShellLayout。

Projects 可拥有自己的条目呈现、详情头部和局部样式。共享字体、颜色、导航与转场保持统一；不为少量交互引入 React 页面应用、全局状态库或第二套滚动引擎。角色如需栏目差异，作为共享角色层的明确配置扩展，不修改文章和相册的既有分支行为。

### URL 与返回

保留现有项目 slug 和 `/projects/<slug>` 深链接；标题改动不自动改 URL。已有 /ai-works 重定向继续保留，不能因栏目重排而删除。详情可直接访问、刷新、新标签打开，不要求先经过首页或开场。

从列表打开详情后返回，恢复本次列表位置和原项目链接焦点；浏览器后退、前进同样可用。从外部直达详情时，“返回项目”明确去 /projects，不尝试退回外部网站。恢复状态只服务本次导航，不创建长期浏览记录。无 JavaScript 时仍可通过普通链接访问内容，增强恢复能力失效也不影响阅读。

## 六 空态 降级与质量要求

零个公开项目时，只显示“项目正在整理。”和正常全站导航，保留 /projects 并设置 noindex；不显示草稿数量、标题、图片或空卡片。未公开详情与不存在路径统一走 404，不泄露“此项目是草稿”。

图片加载失败时，保留项目文字、替代说明和详情入口，不让列表布局跳动；角色失败不影响内容。无 JavaScript 时，列表、正文、外链和返回链接全部可用。页面切换失败不能留下遮罩或空白正文。

链接使用语义锚点、清楚可见的焦点和至少 44px 的有效操作高度。工作／个人及状态不能只靠颜色区分；有意义的图片提供准确 alt，装饰使用空 alt。长标题、长角色说明和无图片条目必须一起检查。

减少动态效果模式取消本栏目非必要过渡，不设置自动循环或滚动触发的表演。辅助图片按显示尺寸提供资源、预留宽高，首屏外懒加载；不新增字体、视频或重型前端依赖。

页面 title、description 与分享摘要来自已批准名称和简介。沿用共享 SEO 基础，不为 Projects 新建自动生成的成就摘要或未经批准的 OG 图片。公开门禁同样适用于构建输出和元数据。

## 七 验收与后续批准

以下是未来实现的验收标准，本轮没有运行产品测试或完成页面验收：

1. 列表不依赖图片与悬停即可回答“这是什么项目、包子做了什么”；工作与个人案例在同一信息层级中成立。
2. 详情能清楚区分个人责任与团队结果；无指标、无图、无结果时没有虚构内容或空模块。
3. 0 条、1 条、多条、长名称、无图片、图片失败、纯工作或纯个人内容均能正常呈现。
4. 360、390、767、768、1024、1440px 及原生 200% 缩放下，导航、角色、列表与正文无整页横溢、遮挡或不可达操作。
5. 鼠标、键盘、触摸、无 JavaScript、减少动态效果均可完成列表进入详情及返回；深链接、刷新、前进后退和快速连续导航正常。
6. 生产列表、详情、首页引用、资源和元数据均不泄露草稿、私有截图或未批准角色；零内容 noindex 保持。
7. 文章 D-150、相册 D-155、既有开场及共享转场通过对应回归；视觉需用户看真实预览确认，构建通过不能替代。

本版不包含 Resume 重设计、新 CMS、搜索、评论、项目统计后台、内容自动迁移、发布、域名或部署调整。只创建本规格，不修改源码、内容批准字段、既有归档或实施报告，也不提交、推送或部署。

请审阅列表的信息顺序、详情中的个人贡献结构，以及人物和嘉乐的安静呈现。确认本规格后，下一步仅编写可审阅的实施计划；计划确认并选定执行方式后才进入代码工作。真实项目材料和新姿态仍分别保留批准关卡。
